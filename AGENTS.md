# Правила для ИИ-ассистентов

AGENTS.md является единым источником правил для всех ИИ-ассистентов проекта.

## Проект

iPhone-Carrier-Manager разрабатывается для проверки, подготовки и установки
операторских профилей IPCC на iPhone через USB. Целевая платформа: Windows.
Язык: Python. Для взаимодействия с устройством предусмотрена pymobiledevice3,
но пока она не добавлена в зависимости и рабочих функций нет.
Зависимостей должно быть минимум. Сервер, GUI, телеметрия и автообновления не нужны.

## Простота

- Соблюдать KISS/YAGNI. Сначала искать возможность упростить или удалить.
- Новую проверку вводить под воспроизведённый случай, описанный в PR,
  а не под теоретическую опасность. Обязательные правила безопасности сохранять.
- Если два последовательных PR исправляли одну функцию, предложить упростить
  или удалить механизм вместо третьего патча.
- Работать только по ТЗ владельца, без механизмов на будущее.

## Безопасность телефона

Уровни безопасности действий:

1. Чтение данных устройства и локальные операции без записи на телефон.
2. Запись с предусмотренным штатным откатом: доверие устройству, временные файлы,
   перезагрузка.
3. Запись без подтверждённого полного отката: установка IPCC и повторная установка
   предыдущего пакета.

- Запись уровней 2-3 допускается только по явному разрешению владельца
  и при подготовленном пути восстановления.
- Автоматически устанавливать доверие между компьютером и iPhone запрещено.
- При неоднозначности SIM-линии, eSIM, версии профиля или целевого устройства
  остановить операцию.
- Исчезновение устройства из USB не подтверждает перезагрузку.
- Успех установки подтверждать только после перезагрузки и повторного чтения
  точной версии профиля.
- Повторная установка прежнего IPCC не гарантирует возврат заводского состояния.
  Не называть её подтверждённым полным откатом.
- Не обещать поддержку 5G, полный откат или совместимость с непроверенными iOS.
- Перед инструкцией к потенциально опасному действию объяснять, что оно делает,
  какие данные меняет и что может не восстановиться после ошибки.

## Данные

- Реальные IMSI, ICCID, UDID, серийные и телефонные номера, Apple ID,
  локальные пути с именами пользователей не добавлять в репозиторий и публикации.
- Полные идентификаторы, если понадобятся в будущих версиях, существуют только
  во временной папке на время операции и удаляются после неё.
  В логах полных идентификаторов нет.
- Не добавлять операторские файлы Apple: .ipcc, .bundle, plist операторских пакетов.
- Тесты используют только выдуманные данные и синтетические пакеты,
  создаваемые самими тестами.
- Не публиковать токены, ключи, пароли, приватные IP-адреса и личные домены.
  Явно опубликованные владельцем реквизиты для пожертвований не являются
  приватными ключами. Переносить их только из указанных владельцем источников.
- При сомнении в безопасности, лицензировании, конфиденциальности, сохранности
  репозитория или реквизитах остановить соответствующее действие и запросить решение.

## Чистая реализация

- Писать код самостоятельно. Не копировать код, названия функций или структуру
  сторонних программ. Не упоминать программы-аналоги в репозитории.
- Использовать публичную документацию и собственные требования проекта.
- Сведения об используемых библиотеках фиксировать в NOTICE.

## Git и PR

- Одна задача = одна сессия = одна ветка от актуального main.
  Не изменять main напрямую.
- Настраивать Git только локально для репозитория: user.name=xPROMSx,
  user.email=102687702+xPROMSx@users.noreply.github.com.
  Автор и коммиттер каждого нового коммита должны совпадать с этими значениями.
  Если платформа этого не позволяет, остановиться до создания коммита.
- Не использовать git config --global, force push и изменение истории main.
- В сообщениях коммитов и PR запрещены Co-Authored-By, Claude-Session,
  Generated with и аналогичные служебные отметки об ИИ.
- Создавать Draft PR. Перечитывать его описание и проверять файлы и HEAD-SHA.
  Без разрешения владельца не переводить PR в Ready for review, не выполнять merge,
  не создавать релизы и теги, не менять GitHub Settings и правила защиты веток.

## Проверки

Уровни проверки отличаются от уровней безопасности действий:

- Уровень 0: CI.
- Уровень 1: Windows с выдуманными данными или чтение уже сопряжённого iPhone.
- Уровень 2: запись на iPhone, только владелец и по его явному разрешению.

Запускать применимые проверки: установку с dev-зависимостями, ruff check и pytest.
Не ослаблять тесты ради успешного результата. Не объявлять невыполненную проверку успешной.
Для подготовки каркаса нужен только уровень 0; действия с реальным iPhone запрещены.

## Документация и отчёт

Писать просто, без эмодзи, длинных тире и рекламных обещаний. Основной язык:
русский; README_EN.md и docs/SUPPORT.en.md: естественный английский.
README двух языков должны совпадать по смыслу и разделам.

В отчёте указать:

- Ссылку на PR, ветку, итоговый HEAD-SHA и исходный SHA main.
- Что прочитано с SHA источников и что не удалось прочитать.
- Изменённые файлы, добавленные и удалённые тесты.
- PASS / FAIL / NOT RUN для каждой проверки с причиной невыполнения.
  Если CI выполняется, сообщить фактический статус, не писать PASS.
- Что проверено и не проверено, возможные регрессии.
- Отличия от ТЗ и вопросы владельцу.
